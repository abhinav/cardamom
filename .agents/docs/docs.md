# Documentation

Use this guide when changing Markdown, user-facing examples, release prose,
or other external text.

The root `README.md` and top-level `USER_GUIDE.md` are generated by Stitchmd.
Edit `doc/readme/README.md`,
`doc/guide/README.md`,
and their linked source files,
then run `mise run docs`.
Do not edit either generated file directly.

Write for readers who do not have the conversation, tool output,
or implementation history.
State behavior and reader decisions before implementation details.

Use stable names for commands, flags, packages, paths, fields,
and domain concepts.
Prefer repetition to an ambiguous synonym.
Do not invent a name for a concept that has no stable referent.

Distinguish observed facts, supported inferences, and recommendations.
Do not invent an owner, required next action, or recovery claim
when the evidence does not establish one.

## Markdown structure

Use sentence case for every Markdown heading.
Keep prose sentences and paragraphs short.

Indent every paragraph, code block, or nested list
beneath an ordered or unordered list item by exactly four spaces.
Add exactly four more spaces for each deeper list level.

## Semantic line breaks

Use semantic line breaks in Markdown, multi-line comments, commit messages,
and changelog prose.
Start a new line at a sentence boundary, before a long clause,
or where the subject changes.

Do not put every phrase or comma-separated item on its own line.
Keep prose near 80 columns and within 100 columns unless a link or code span
requires more.

## Examples

Keep command examples executable.
Use structured output in automation examples and parse the emitted value or
JSON Lines stream rather than human-readable output.

Do not include implementation detail unless the reader needs it to understand,
evaluate, or safely use the documented behavior.
